# METIS 生产站与开源仓审计

审计日期：2026-08-12  
目标：`https://metisziwei.com/` 生产站，以及关联 MIT 仓库 `Renhuai123/ziwei-doushu`  
方法：在用户已登录的 Chrome 中做只读页面审计；用虚构出生资料 `2000-01-01 08:00，男` 走通免费起盘；不点击购买、第三方绑定、退出登录或发送反馈。测试产生的虚构历史记录已触发删除操作。

## 一句话结论

METIS 真正值得 FateRadar 采用的不是它的紫微算法，而是这条产品骨架：**任务入口 → 单页输入 → 同 URL 即时进入“盘面 + 解读”工作台 → 本命/大限/流年等时间层切换 → 免费核心内容 → 登录保存与专业版扩展**。

但当前生产站明显已经超出公开仓库。MIT 仓库能直接提供的是旧版 Demo 组件与结构；生产站独有的工作台、账户、订阅、三纪地图和大量内容路由需要重建，不能把“页脚链接 GitHub”理解成生产前端全部开源。

## 1. 已走通的真实用户旅程

### 1.1 首页

首页是视觉化任务选择器，不是传统产品介绍长页：

- 紫微命盘 `/chart`
- 合盘分析 `/heming`
- 命运双胞胎 `/twins`
- 三纪 `/sanji-map`
- 学术中心 `/academy`

桌面页头保留起盘、合盘、账户、语言与普通版/专业版状态；移动端菜单补齐三纪学习、知识库、古籍库与账户。

### 1.2 单人起盘

`/chart` 的输入合同：

- 姓名可选
- 公历/农历切换
- 年、月、日
- 小时、分钟，并即时显示对应时辰
- “不知道出生时间”开关
- 出生地，用于真太阳时校正
- 男/女
- 提交前摘要

重要交互不是“资料缺失就报错结束”，而是分两步提醒：年月日缺失走浏览器原生必填校验；日期完整但没填出生地时，第一次提交在原位提示“强烈建议填写出生地”，第二次允许用户确认按北京时间继续。

### 1.3 免费结果页

提交后 URL 仍是 `/chart?...`，页面直接从输入态切换为全屏工作台：

- 顶栏：返回、本命/大限/流年/流月/流日/流时、升级、流派、导出、历史、反馈
- 左栏：十二宫命盘、中心出生资料与关键字段、大限、流年、流月、流日、流时
- 右栏：命盘分析/AI 对话、主题切换、雷达图、核心优势/关系模式/成长课题、完整正文、命盘依据、古籍出处、风险提醒
- 时间交互：点“流年”后，盘面直接叠加流年宫位、流曜、流年四化，同时保留本命与大限参照
- 流派弹窗不是一个模糊“高级设置”，而是 9 类可解释规则：主星亮度、庚年四化、天马、天空、截空旬空、魁钺、天使天伤、长生十二神、晚子时、闰月归属等

免费版可读六个核心主题：命格总览、财运、事业、感情、性格、健康。专业版再打开兄弟合伙、子女、迁移外出、人际贵人、田宅、福德、父母长辈，以及全盘报告和更细时间层。

## 2. 账户、保存与付费层

登录态账户中心实测可见：

- 手机登录，邮箱可绑定
- Google / GitHub / X / Apple 可绑定为同一账户
- 会员状态与 AI 提问额度
- 修改密码、退出登录
- 历史记录分命盘、合盘、AI 对话

专业版页是 Free / Pro 对照，不是零散弹窗：Free 提供六维、本命与大运、预生成解读；本次 Chrome 登录态页面显示 `¥168` 永久买断，公开页面的其他响应当前也出现 `¥148 / 原价 ¥168` 与“请在 App 内开通”状态，说明价格/渠道仍会按部署状态变化。Pro 提供十三宫、流月/流日/流时、每日 AI 额度、自有 API Key 通道、三纪典藏与 PDF。审计只读取权益，没有点击微信或支付宝支付。

这里对 FateRadar 的启示是：**UI 可以先完整预制，但权益必须以真实 capability 与 entitlement 状态驱动**，不能靠隐藏 DOM 或文案假装开通。

## 3. 其他产品入口

### 合盘 `/heming`

甲乙两套完整出生表单并列，定位为感情、合伙、亲子、朋友。当前“开始合盘分析”明确属于专业版。它是独立双人产品，不是单人结果页里临时加第二个人。

### 命运双胞胎 `/twins`

用单人出生资料查同盘配置，页面同时解释匹配维度、非匹配维度、能力路线图和数据规模。该功能不是公开 MIT 仓库路由，属于生产站新增产品层。

### 学术中心 `/academy`

学习入口分为天纪、地纪、人纪；同时提供新手路径、课程目录、知识库、14 主星、24 组双星、37 种格局和古籍库。它把“工具”和“知识证据”做成了互相可达的产品，而不是在结果页底部堆来源链接。

### 三纪地图 `/sanji-map`

生产页使用一个全屏同源 iframe 加载独立静态应用，包含 21 个学习任务节点和天纪/地纪/人纪/学术中心四类路径。当前控制台稳定出现 React hydration `#418` 与 segment fetch failed；可见首屏仍能渲染，但这是一个真实生产缺陷，应避免照搬这种 iframe 双应用架构。

## 4. 响应式实测

| 视口 | 输入页 | 结果页 |
|---|---|---|
| 360×800 | 无横向溢出；表单宽 332；年月日三列、时分两列；完整移动菜单 | 双栏变纵向：520px 盘面先按 360px 缩放，解读接在下方；页面约 7700px 长；顶栏两行 |
| 768×1024 | 桌面导航已经出现；表单保持 432px 居中 | 仍是左右栏：左栏固定 520px，右栏只剩约 237px；主题自动多行，正文约 205px 宽，可用但明显拥挤 |
| 1024×768 | 表单 432px 居中，无横向溢出 | 左栏固定 520px，右栏约 493px；两栏各自滚动，进入正常工作台状态 |
| 1440×900 | 表单 432px 居中 | 左 520px + 右 909px；顶栏 52px；工作台占满剩余高度，左右独立滚动 |

起盘页移动导航的实际切换点在约 520px，而不是 768px。结果工作台则在手机宽度直接纵向重排；768px 已强制两栏，因此平板竖屏的右栏过窄。FateRadar 不应原样复制这个缺点：建议把八字工作台的“单列 → 双栏”断点放在内容真正容得下的宽度，至少让右侧阅读栏不低于 360px。

仓库自己的 `app/chart/page.tsx` 明说该页只是最小 Demo，线上重设计 UI、AI 流式解读等商业交互不在开源范围。公开仓库仍有旧域名硬编码，而线上 sitemap/robots 已切到新域名，也说明两者不是同一份部署源码。

生产站当前 sitemap 约 285 条：17 个一级页、243 个知识详情、6 部古籍、3 个指南及 16 个 `/sanji/*` 页面；`/account`、`/history`、`/settings/model`、`/sanji-map` 等公开可达但不在 sitemap 或带 `noindex`。这套规模远超公开仓库的首页、chart、heming、knowledge、library、preview、privacy、terms 路由。

## 6. 对 mingli_web 的直接决定

FateRadar 的施工基线应固定为：

1. **算法权威不变**：自有 Runtime 是唯一命理事实源。
2. **青囊定义产品版图**：单术数、三术合参、问事合参与术数选择都按已审计的青囊模式组织。
3. **METIS 定义任务页和工作台骨架**：单页输入、同页出盘、盘主文辅、时间层、主题栏、历史/导出/设置入口和响应式状态。
4. **开源代码只取表现层**：MIT 组件可以复用或适配；`generateChart`、真太阳时粗算、三方四正、四化、判格、prompt 拼装、localStorage 出生资料等客户端算法全部剥离。
5. **先预制完整 UI**：每个未来功能都有 loading、empty、ready、locked、need-input、error 六态；没有算法的数据使用明确 fixture / locked 状态，绝不回退显示 raw JSON。
6. **当前本地最大差距**：现有 `/app/profile/new → /app/profiles → /app/bazi → /app/readings/:id` 把一个任务拆散。目标应收敛成 `BaziTaskFlow → BaziMatrix → BaziInspector`，再接版本化 `BaziChartViewV1`。

## 7. 已发现的 METIS 自身问题

- `/sanji-map` 静态应用有 hydration 和 segment fetch 错误。
- 768px 竖屏仍固定 520px 左盘，右侧阅读栏过窄。
- 未填出生地需要连续点两次同一 CTA 才继续，意图明确但反馈可更像确认动作。
- 日期必填只使用浏览器原生校验，产品内没有统一错误摘要。
- 结果页 URL 暴露出生年月日时与性别参数；FateRadar 应继续用服务端版本/句柄，不照抄这种 URL 合同。
- 结果页首屏信息极密，手机虽然无横向溢出，但内容总长很大，必须提供粘性章节导航或折叠策略。
