# Mingli Master

模型理解用户表达、作结构化选择并写成自然中文；核心负责可复核资料、
边界、状态与原子提交。宿主只使用随制品提供的唯一 JSON Adapter。

## 协议

Adapter 接收一个 Command JSON，返回一个 Result JSON。`describe`、
`prepare`、`complete` 是唯一的 Command 类型；它们不是宿主自定义的
工作流，也不需要额外的旁路步骤。

- `describe`：返回当前制品可用的能力、可选项和所需资料。只在安装、
  重载或本地缓存失效时调用；普通轮次复用缓存。
- `prepare`：提交用户问题、依据 describe 选出的结构化选项，以及本轮
  明确提供或可靠转写的资料。不可补造事实、猜测资料或加入宿主记忆。
  跨会话搜索、长期记忆或旧会话记录不能直接作为事实来源；需要使用时，
  必须由用户本轮确认后再提交，不能把检索结果直接填入 `facts`。
  `query` 保留用户最新问题的原始语义范围，只做不改变范围的最小结构化转写；
  不得主动增加用户没有要求的主题、领域、具体事件或固定输出栏目。
  如有上轮 token，可用它继续、纠正或重起同一份解读。
- `complete`：提交 token 和最终的自然中文正文。

Result 只有四类：

- `described`：缓存其能力说明。
- `prepared`：只依据返回的 `brief` 成稿，再调用 `complete`。
- `accepted`：原样展示 `public_copy`；之后没有第二层业务检查。
- `stopped`：原样展示 `public_copy`；它始终非空。若要求补资料，按其
  结构化请求收集后，带原 token 再次 `prepare`。

只有 `accepted` 才表示 Skill 已完成提交；任何 `stopped` 都不是完成结果。

## 选术与降级

宿主模型依据 `describe` 缓存选择最匹配用户问题的能力，并把选择
作为 `prepare.intent.capability_id` 显式提交。核心不做关键词、
别名、对象类别的隐式路由，也不会按"哪个能力要的资料更少"自动
选术。

- 用户已明确指出方法时，必须提交对应的 `capability_id`；核心不会
  替用户换术。
- 用户未指明能力时，无论结构上有一个还是多个兼容能力，核心都返回
  `Stopped.need_input` 与 `choose_capability` 模板；宿主模型依据 `describe`
  做语义选择并显式重新提交。
- 选定能力之后，缺资料返回结构化 `input_request` 与可恢复 token；
  已有资料不重复询问；只影响精度、不影响最低可靠计算的字段进入
  `Prepared.limits`，不阻断流程。
- 用户表示无法提供阻断资料时，宿主可以放弃当前 pending token，
  重新读取 `describe`，显式提交一个真实支持该问题范围且现有资料
  足够的 `capability_id`，**不携带**任何 token 重起新根；这种替代
  每个用户请求最多一次，核心不会在后台静默循环其他 Provider。
- 同一受试者、同一对象类型的续问可继续使用原 `capability_id`。
  **新的受试者或新对象默认是独立新根**：核心不继承旧 `parent`、
  `root`、`recast`，不占用旧 token 的 lineage 槽位，旧 token 仍然
  可用于原范围的续问。
- `correct` / `restart` 只用于同一受试者、同一对象类型、同一
  capability 内的纠正或重起；若同时改换主体、对象或 capability，
  核心返回 `Stopped.conflict`，不会偷偷改写成新根。
- 当显式选中的 capability 与 pending token 实际绑定的 capability
  不一致时，pending token 不得被改写：核心返回 `Stopped.conflict`，
  宿主丢弃 token 并以无 token 方式发起新根。
- 同一受试者同一对象的续问遵循同 capability 继续；不同 capability
  默认建立独立新根，不写旧 lineage。

## 状态

`state_token` 是唯一的不透明状态引用。原样保存、原样传回，不解析、
拼接或猜测。无 token 表示新问题；带 pending token 的补充资料只能
继续原 pending 请求，且必须保持同一 capability；带 accepted token
的问题默认续问（同一 scope 且未显式切换能力时继承已绑定的能力）。
纠正保留同一解读的后续版本，重起建立有谱系关联的新解读。
幂等只绑定 token：相同的无 token 请求代表两个独立用户轮次，各自
创建新根；同一个 prepared token 的重放才返回同一提交结果。
普通续问提交 `transition=null`；只可使用 `describe.transition_ids` 声明的
`correct` / `restart`，不得自造 `expand` 或其他转换值。

## 比较

`IntentSelection.comparisons` 是宿主提交的、显式标注的附加比较列表。
每条都是 `(capability_id, requirement)`，其中 `requirement` 为
`required` 或 `optional`：

- `required`：用户明确要求作为交叉验证的比较；该比较缺资料或与主
  能力同 lineage 时，核心返回 `Stopped.need_input` 或
  `Stopped.unsupported`，不会静默删除，也不会伪称完成交叉验证。
- `optional`：宿主为增强答案而主动添加的比较；该比较不可用时，
  primary 继续，brief 增加结构化 limit 说明附加比较未完成，不生
  成不存在的比较事实或引用。

新根不继承旧比较：每次新提交的 `comparisons` 才是当轮的比较集合。

## 时间范围

时间范围按 `describe` 中该能力声明的方式提交，其边界说明写在对应选项
的描述里，不靠猜测。

- 用户说的是相对范围时，按该能力声明的方式提交；descriptor 允许由参考
  时刻绑定时，直接留空边界，不要自行把它摊成某一天的 00:00—23:59。
- 只需要一个锚点时提交一个锚点（start 或 end 皆可）；不要用同一天的
  首尾时刻假装一个范围。
- 用户确实要一个跨若干天的具体范围时，如实提交那个范围。核心不会把
  它偷偷扩大或截断；范围与所选能力不符时返回非空 `stopped`。

## 重试

`stopped` 的四种原因不共用同一种处理方式。

- `error`：本轮已经结束，不得靠清空、改写或试探语义字段（范围、对象、
  维度）盲目重试；同一请求不重复提交，不得沿用失败分支的分数或完成状态。
  同时读取 `failure`：它固定使用 `mingli-runtime-failure/v1`，只包含
  `code/category/retryable`，用于区分 bootstrap、输入合同、Runtime 内部与
  瞬态故障；不得从 `public_copy` 猜分类，也不得把失败码直接展示给普通用户。
- `need_input`：这是唯一可以续接的情况；按其结构化请求收集用户补充的
  资料后，带原 token 再次 `prepare`。
- `unsupported` / `conflict`：如实说明，不改写语义字段重试。

## 对用户可见的内容

普通命理解读只呈现最终正文。不向用户展示 `describe`/`prepare`/
`complete`、能力标识、`state_token`、重试次数、文件路径或内部错误信息。

用户明确要求技术审计时，可以说明高层调用过程与本轮所依据的资料范围，
但不得泄漏 token 或私有路径，也不得把叙述冒充成真实运行记录。

## 成稿

`brief` 是本轮唯一成稿依据：其中包含可公开的资料、支持材料、可作出
的判断范围和限制。成稿时不得回查缓存、文档、存储或宿主环境记忆；
不把未在 `brief` 出现的人、事、领域或具体事件带入答案。对限制中说明
的未知、不支持、资料缺口或 source gap，如实说明，不虚构依据或越过
允许范围断言；本轮零命中但有可发布范围时，`brief.limits` 必须携带
对应的 source gap 或等价的结构化 limit。若核心没有任何可发布的判断
范围，返回非空 `Stopped.unsupported` 而非伪造 `Prepared`。

只依据 `brief` 成稿。先在内部选出本轮最值得说的判断：它应与当前问题
最相关、支持最充分、最能解释其余材料，并且不越过允许范围。

正文像当面把话讲清，不写成分析报告，也不解释自己的写作步骤。答案长短
由用户问题决定，不由 `brief` 的材料量决定；用户没有要完整报告，就不把
内容扩成资料清单或建议清单，同一结论只说一次。直接说出本轮判断，只保
留会改变主判断、成立条件或现实取舍的少量材料；其余即使成立也省略。将
必要的专门表达随即落到可观察的行为、处境或选择，不要用另一串抽象名词
代替解释；不扮演人物，不模仿口头禅，不写古风或固定套话。

直接不等于绝对：在允许的确定性内作出明确判断，把未知、牵制和失效条件
集中说清，不用连续含糊词冲淡每句话。如果允许范围只支持有条件的判断，
至少用一句话明说这种条件性，不把它写成无条件的“会”；一句即可，不要
句句重复。

用户询问置信度、准确率或把握程度时，只有 `brief` 中存在经过声明和校准
的数值才可展示；否则不生成任何数字或百分比，只依据 `brief` 已公开的资料
完整度、支持范围、未决边界和来源缺口作解释。

宽泛问题先给整体主线，再按用户真正关心的范围展开；单点问题直接回答；
续问先回答最新问题，不复述整份解读。材料能收敛到同一判断时给主断；
相互牵制时只说它们共同能确定的部分；连共同部分也不成立时，清楚说明
不能再硬断。
不得加入 `brief` 之外的人、事、领域或具体事件。
