# 命理网站产品方向 v2.0

> 决策日期：2026-08-09  
> 状态：Accepted，作为当前产品定位与范围基线  
> 取代：v1.0 的“微信小程序优先”平台方向  
> 权威商业化与技术合同：[PRODUCT_BLUEPRINT_WEB_IOS_V2.md](./PRODUCT_BLUEPRINT_WEB_IOS_V2.md)  
> 共同语言：[CONTEXT.md](../CONTEXT.md)

## 一句话结论

第一版做一个 **移动端优先、桌面端完整可用的响应式命理网站**，定位仍是“个人命理档案 + 一事一问 + 事实核对”；后续做独立的原生 iOS App，共用同一套账户、商品、权益、命理解读和历史数据后端。

网站不是桌面专业工具的缩小版，也不是套着命理提示词的聊天框。首屏直接让用户完成三件事：

1. 建立命理档案并查看八字概览；
2. 查看今日与近七日；
3. 围绕一件具体事情起六爻并得到结论。

## 1. 已冻结的长期方向

以下决定进入开发后不随页面喜好反复调整；如确需改变，必须新增 ADR、迁移方案和回归测试：

1. P0 先做网站，不再把微信小程序作为首发载体。
2. 网站采用响应式布局和 PWA 基础能力，但 PWA 不是原生 iOS App 的替代品。
3. P2 的 iOS 客户端采用原生 SwiftUI，共用后端，不把网站 WebView 当正式 App。
4. 内部 User ID 是账号根；手机号、邮箱、微信和 Apple 只是可绑定的登录身份。
5. P0 只卖两种绑定具体解读目标的单次商品，不卖永久无限 AI，不做自动续费。
6. 网站支付、未来 Apple 内购和未来周期扣款都通过渠道适配器接入同一订单与权益账本。
7. 支付成功、权益授予、解读生成和正文交付分别建模；客户端“支付成功”页面不是真实到账依据。
8. mingli-master 是唯一命理事实、古籍证据和连续状态核心；模型只负责受约束的白话成稿。
9. 档案、事实简报和已接纳正文不可变版本化；反馈不能暗改盘面。
10. 首版仍采用阿里云上的模块化单体，不提前拆微服务，也不在业务服务器上硬塞大模型。

## 2. 产品服务谁

### 首要用户

对传统命理感兴趣、但看不懂专业盘面，希望围绕事业、关系、阶段选择获得一份白话、可核对、可继续追问的普通用户。

### 次要用户

专业命理工具的客户接收方。专业端以后可以生成或分享报告，用户在网站或 iOS 中查看、核对现实信息并继续追问。

### 首版不服务

- 需要规则编辑、批量客户管理和流派参数面板的专业命理师；
- 只追求随机测试、抽签裂变和娱乐排行的用户；
- 希望产品替代医疗、法律、投资、心理或婚姻专业意见的人；
- 希望购买“改运”“消灾”或确定结果承诺的人。

## 3. Metis 参考边界

第一版参考 [Metis紫薇](https://metisziwei.com/) 的网页表达方式和账户、支付路径，但不复制品牌、素材、页面代码或未开源后台。

| 参考点 | 我们采用的原则 | 我们不会照搬的部分 |
|---|---|---|
| 大字号标题、场景化大卡片、固定简洁导航 | 首页先讲用户能做什么，再进入工具 | 不复制 METIS 字标、图片、动效和具体版式 |
| 起盘前不强迫登录，登录后保存历史 | 游客可完成免费试算；保存、追问和付款前登录 | 不把出生资料和正式报告长期留在 localStorage |
| Free 与付费权益并排说明 | 商品页明确展示免费边界、付费交付、期限和追问次数 | 不做“永久 Pro + 每日持续 AI”承诺 |
| 手机、邮箱等身份可归并到一个账号 | 一个 User 绑定多个 Login Identity | P0 不复制复杂密码体系和全部社交登录 |
| 桌面微信扫码、移动端支付宝/微信路径 | 按浏览器环境选择官方网页支付产品 | 不复用对方 API、商户配置或订单逻辑 |
| App 内与网页支付入口分离 | 未来 iOS 只用 StoreKit 2 解锁数字内容 | 不靠 URL 参数或隐藏按钮规避审核 |

公开仓库 [Renhuai123/ziwei-doushu](https://github.com/Renhuai123/ziwei-doushu) 可参考排盘 UI、响应式布局、表单和开源算法，但其 README 已明确：登录、短信、会员、支付、后端 API 和部署配置不在开源范围内。因此账户与支付只能参考公开交互，不能当成可直接复用的完整系统。

## 5. 首页与关键页面

### 首页

首页采用编辑型落地页，而不是空白聊天框：

1. 首屏：一句价值主张、一个主按钮“免费建立命理档案”、一个次按钮“问一件具体的事”；
2. 三张任务卡：命理档案、今日与近七日、一事一问；
3. 方法说明：先确定性计算，再由模型白话表达；
4. 示例结果：展示结论、依据、边界和核对方式，不展示真实个人资料；
5. Free 与单次付费对比；
6. 隐私、AI 标识、备案和支持入口。

视觉采用自有的深墨绿、米白和低饱和金色体系。移动端单列、桌面端双列或三列；重要按钮点击区域至少 44px；动效必须支持减少动态效果偏好。

### 建档页

按步骤只收真正需要的数据：

1. 姓名或称呼，可选；
2. 公历/农历出生日期；
3. 出生时间，允许“不确定”；
4. 出生地与时区；
5. 真太阳时口径的明确开关和解释；
6. 性别及必要的术法口径；
7. 提交前资料确认和隐私同意。

游客可以试算，但页面刷新或草稿过期后不保证保存。登录后才把确认过的 Profile Version 永久保存。

### 结果页

内容顺序固定为：

1. 先给结论；
2. 再说明成立原因；
3. 再说边界、条件和不确定性；
4. 提供三条现实核对；
5. 命中古籍证据时展示来源；
6. 最后提供同盘追问或购买深度解读。

免费概览和付费报告是两个独立 Reading Root。付费不是把已经展示的残缺文字补齐，而是用户确认一个新的、边界明确的购买目标。

## 6. 账户方向

### P0 登录方式

- 主要方式：中国大陆手机号验证码；
- 备用方式：邮箱验证码；
- 条件成熟后：微信网页 OAuth；
- iOS 上线时：Sign in with Apple，并允许与现有账号安全绑定。

P0 默认无密码，减少弱密码、找回密码和撞库风险。未来若数据证明用户确实需要密码登录，再作为新的 Login Identity 类型增加，不改变 User 根模型。

### 游客与登录边界

- 游客可浏览公共内容、填写资料和完成有限免费试算；
- 保存档案、跨设备历史、核对反馈、追问、购买和退款申请必须登录；
- 游客草稿使用短期 Guest Session，登录后可一次性认领；
- 不允许用手机号、邮箱、微信 OpenID 或 Apple subject 直接当业务主键。

### 会话安全

- 网站使用 HttpOnly、Secure、SameSite Cookie 和 CSRF 防护；
- 浏览器 localStorage 不保存正式访问令牌、完整报告或长期出生资料；
- iOS 使用 Keychain 保存会话凭据；
- 用户可以查看并撤销其他设备会话；
- 账户合并需要双方身份重新验证并写审计日志。

## 7. 免费与付费内容

| 层级 | 交付 | 价格 |
|---|---|---:|
| 免费 | 一个本人档案、确定性八字排盘、有限白话概览、3 条事实核对、今日/近七日摘要、六爻基础卦象 | ¥0 |
| 个人命盘深度解读 | 绑定一个档案版本的主题报告、永久查看、7 天内 3 次同盘追问 | ¥29.90 |
| 一事一问·六爻 | 绑定具体问题和卦象的事件报告、永久查看、72 小时内 2 次同盘追问 | ¥9.90 |

P0 不卖自动续费、代币钱包、充值余额、无限 AI、用户自带 API Key 或“永久包未来所有计算”的会员。

原因很直接：报告永久查看是有限的存储成本；“永久每日 AI”是无限期模型成本，两者不能混成同一个买断承诺。

## 8. 自动续费与自有模型

自有模型和自动续费是两件事：

- 用户付费渠道负责扣款、续费、退款和通知；
- Model Gateway 负责调用自有模型 API 或独立推理服务；
- 自建 GPU、云服务器或模型 API 账单属于企业运营成本，不代表用户已经续费；
- 用户每次续费成功后，系统新建一个 Subscription Cycle，再向权益账本授予当期额度；
- 模型故障不能把未交付权益当成已经使用，也不能改变用户订阅状态。

P1 只有在留存、成本和渠道准入都通过后，才增加“连续陪伴订阅”：

- 网站：经审核开通的微信委托扣款或支付宝周期扣款；
- iOS：Apple 自动续期订阅；
- 同一个用户跨端只允许一个同类有效合同，避免重复扣费；
- 取消续费只阻止下一周期，不提前收回已经付款周期的权益。

## 9. 程序与算法方向

系统分为三层，职责不能混：

1. 确定性命理层：规范化历法、时间地点、排盘、事实、证据和连续状态；
2. 受约束表达层：模型依据 Fact Brief 生成自然中文，不自行算盘或补造证据；
3. 产品交付层：账户、订单、权益、任务、报告、追问、隐私和展示。

标准执行链固定为：

~~~text
输入确认 → Profile Version → mingli prepare → Fact Brief
→ 商品/平台合同校验 → Model Gateway 成稿 → 事实与结构校验
→ mingli complete → Accepted Copy 落库 → 权益核销 → 交付
~~~

任何模型厂商、自有模型或提示词变更都只能发生在 Model Gateway 后面，不能侵入命理核心或改变已接纳正文。

## 10. 发布阶段

### P0：响应式网站

- 公共落地页、方法页、价格页和合规页；
- 游客试算与手机号/邮箱登录；
- 一个本人档案、八字概览、3 条核对；
- 今日/近七日；
- 六爻一事一问；
- 两种单次付费、订单查询、退款和永久报告库；
- 数据导出、删除、设备会话和支持入口。

### P1：留存与订阅验证

- 更多复访内容和通知偏好；
- 达到指标后灰度连续陪伴订阅；
- 微信/支付宝周期扣款仅在商户资质实际获批后启用；
- 不因为已经设计了表结构就默认对外出售订阅。

### P2：原生 iOS

- SwiftUI 客户端；
- Sign in with Apple；
- StoreKit 2 单次内购和必要时的自动续期订阅；
- App Store Server API 与 Server Notifications；
- 同一 User、Profile、Reading 和 Entitlement；
- App 内不展示站外数字内容购买按钮。

## 11. 成功标准

P0 不以页面数量为成功，而看以下闭环是否成立：

- 用户能在 3 分钟内完成资料确认并看到第一条有边界的免费结果；
- 游客登录后不会丢失当前草稿；
- 同一订单和回调重复到达不会重复发权益；
- 模型失败不会误扣权益；
- 付费后能查到明确交付进度，并最终得到不可变报告；
- 用户能理解免费与付费差异、追问次数和有效期；
- 删除账号、导出数据、撤销设备和申请售后都有可执行入口；
- 网站在手机与桌面端都能完成完整付款和查看流程。

## 12. 变更控制

可以通过配置和新版本迭代的内容：视觉素材、首页排序、模型供应商、模型版本、新商品价格、支付渠道开关和文案。

不能直接覆盖修改的内容：历史商品版本、订单金额、已接纳正文、档案版本、权益账本、支付渠道原始通知和用户同意记录。

如需改变平台顺序、账户根模型、权益核销时点、命理核心边界或 P0 商品语义，必须先新增 ADR，并附数据迁移、回滚和合同回归方案。
